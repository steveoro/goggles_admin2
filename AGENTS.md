# Goggles Admin2 Agent Notes

## DataFix V2 canonical source handling

- `DataFixController` maps LT2 inputs to persistent sibling `-lt4.json` working copies via `resolve_working_source_path` and `materialize_lt4_working_copy`.
- Reuse existing LT4 working copies when present; regenerate only when missing.
- Exception 2 — manifest copies give way to results: a `<base>-lt4.json` written by `PdfManifests::Extractor` (`_meta.meeting_only: true`) shares the working-copy name. When the LT2 sibling `<base>.json` later has result rows, `DataFix::SourceResolver` (whether given the LT2 or the `-lt4.json` path) backs the manifest file up as `<base>-lt4.orig[-N].json`, re-materializes the LT4 from the LT2 (Layout2To4), and asks `DataFix::Pipeline#invalidate!` to delete `<base>-lt4-phase1..5.json` plus their `data_import_*` rows. While the LT2 is still result-free (`sections: []`), the manifest copy is reused as before. File names are deliberately unchanged, because archives, `CrawlerCalendar::Row#source_state` and `DataFix::CommitArchiver` depend on them.
- `DataFix::Pipeline#invalidate!` is the only path that deletes phase files (manifest supersede, category normalization, the operator's category recompute and "Rebuild (discard edits)"). It backs every existing phase file up (`-phaseN.orig[-N].json`) and deletes NOTHING when one of the target phases holds operator edits (a file without a `_meta.built` stamp counts as edited): the source is then marked blocked (`Ops::PipelineSource` stage `blocked`, reason `source_changed_under_edits`) and the step header offers "Rebuild (discard edits)", the only forced invalidation besides the confirmed recompute.
- When `PdfManifests::Extractor` finds the output already present: a results source is never touched (skip reason `results source already present`, even with `force`); a previous manifest output is skipped unless `force` (`output already exists`); a result-free plain working copy with no phase files is backed up (`.orig.json`) and replaced by the manifest LT4 (with phase files it is skipped unless `force`, and then backed up). Both skip reasons still archive the PDF/.txt (`PdfManifests::Extraction` ends them as done, message `skipped: <reason>`).
- Manifest LT4 files carry `meetingURL` / `manifestURL` from the crawled `<base>.json` (when present and non-blank) right after `layoutType`.
- Phase review/update/add/delete actions must use the canonical source path and propagate `file_path` in redirects.
- Phase1 fixture sources use `layoutType: 4` to keep existing phase-path assumptions stable.

## Phase 1 DataFix pool/city rehydration

- The rehydration lives in the `session-card` Stimulus controller (`app/javascript/controllers/session_card_controller.js`; there is no global `window.DataFix` helper): `selectPool` (change on the "existing pools in this city" select) and `populateFromExisting` re-fetch the pool and its city through the API, `cityIdChanged` (change on the city hidden id) re-fetches the city; shared DOM helpers in `app/javascript/lib/form_fields.js`.
- `_session_form_card.html.haml` wires them with `data-action` attributes (no inline handler is allowed under `app/views/data_fix`: `spec/data_fix_inline_handlers_spec.rb`).
- `Phase1SessionUpdater` detects `swimming_pool.id` changes and overwrites pool/city fields from the DB pool/city, clearing city fields when the selected pool has no city.
- Request specs for rehydrate, city-clear, and stale-city overwrite are in `spec/requests/data_fix_controller_phase1_spec.rb`.

## Calendar meeting selection before result crawling

- `/sources/calendars/meetings?path=…` ("Select meetings" on a CSV of the Sources Calendars tab) renders one row per meeting with URL/manifest/source state; its form posts `kind=calendar_results` + `selected_rows[]` + `rows_count` to `POST /sources/crawls`, which writes a `<base>-sel-<ts>.csv` subset next to the source and queues a `SourceCrawlJob` on it (the crawler is never called in the request). "Crawl all" on the tab queues the whole file. The Calendars tab lists the originals, the `-sel-` subsets, the `-skip` leftovers and `calendar.done` separately.
- `CrawlerCalendar::Sheet`/`Row` (`app/strategies/crawler_calendar/`) are FAITHFUL Ruby ports of the JS crawler's `normalizeText`/`parseDaysDate`/`getOutputJSONFilename` — including quirks (`undefined-` basename for dateless rows, `2026-10-8_11-31` for `31/10-8_11`, cancelled only on literal `true`/`canc`). The predicted `manifest-<date>-<name>.pdf` must match `results-crawler.js` byte-for-byte — keep them in sync when touching either side.
- Manifest state per row: `:done` (pdf in `manifests.done/<season>/`), `:pending` (in `manifests/<season>/`, awaiting extraction), `:none`; source state reports `-lt4.json`/`.json` presence in `results.new`/`results.done`.

## PDF manifest extraction (meeting data)

- `rake manifests:extract season=<id> [engine=devin|ollama]` turns `crawler/data/manifests/<season>/manifest-*.pdf` into `layoutType: 4` sources under `crawler/data/results.new/<season>/` via `PdfManifests::Extractor`. The LLM client is resolved by `PdfManifests::ClientFactory` (param > `MANIFEST_ENGINE` env > default `devin`): `devin` spawns `devin -p` non-interactive sessions (default model `swe-2-high`, requires `devin auth login`); `ollama` uses the local Ollama server (default `gemma4:e4b`, vision fallback only when the model advertises `vision`). Successfully-extracted and already-extracted manifests (.pdf + .txt) are moved to `crawler/data/manifests.done/<season>/`; the task aborts with a warning when the engine or its configured model is not available.
- One extraction path (phase 15): `PdfManifests::Extraction.call(pdf_path:, engine:, data_root:)` = engine preflight (`.preflight_error`), `Extractor` on one PDF, `.archive` (.pdf + .txt → `manifests.done/<season>`); outcome `status` `:done`/`:failed` + the activity message (`extracted (N events)`, `skipped: …`, `extraction failed: …`, `LLM engine unavailable`). Used by `ManifestExtractJob` (`perform(season_id:, fin_event_id: nil, pdf_path: nil, engine: nil, run_id: nil)`: a FIN id from the board/planner, or a PDF path from the Sources Manifests tab, which must resolve inside `manifests/<season>`) and by `rake manifests:extract` (inline, one file at a time, preflight once, same console output, same `src:<sha1>` activity entries as the UI). The Manifests tab queues one job per file, or "Extract next 20" at priority 10 (`Sources::ManifestQueue`). There is no other extraction path (no in-page batch, no status file, no polling). The meeting selection page only accepts CSVs under `crawler/data/calendar.new/<season>/` (`Sources::FileGuard`, realpath-checked), since the crawler only moves `calendar.new` → `calendar.done`.
- Manifest LT4 files carry extra prefill keys: `venueName`, `venueAddress`, `cityName`, `poolLength`, `edition`, `maxIndividualEvents`, `manifestSessions` (one per meeting day) — `Phase1Solver` prefers them over `place`.
- Manifest files are meeting-only (no results): they can be committed as a bare meeting structure after Phase 1 (`Import::StructureValidator` gates the commit; new meetings get `manifest: true`). Results are added with a second data-fix pass on the published-results source — select the existing meeting in Step 1 and rescan sessions to avoid duplicates.
- `Lt4Builder` emits structured `issues` (retriable vs advisory) alongside `_meta.warnings`; `ProgramScanner` adds a completeness hint (program mentions vs extracted events). Retriable issues trigger ONE corrective extraction pass (`ExtractionPrompt.build_correction` feeds issues + valid event codes back to the model); the retry is kept only when strictly better. Never auto-remap unknown event codes.
- `_meta.warnings` from the LT4 source render as an info banner on the Phase 1 review page.
- Devin engine gotcha: the spawned `devin` must not see agent/IDE context env vars (`ACP_BACKEND`, `AI_AGENT`, …) — `DevinClient::SCRUBBED_ENV_KEYS` unsets them, otherwise the nested CLI reports "Not logged in" even with valid credentials. Ollama calling conventions/gotchas (must set `num_ctx`, `think:false`, `format:'json'`): `docs/pdf_processing/ollama_extraction_notes.md`.

## Season board

- Purpose: `/season_board` (`SeasonBoardController`, `app/services/season_board/**`, `app/components/season_board/`) is the weekly one-page flow for the latest MASFIN season: one row per FIN "Riepilogo Eventi" row, with the linked local meeting, a pipeline state and a single next action. Operator guide: `docs/season_board.md`.
- Link key: the numeric FIN event id (`FINEventId`, parsed from results/manifest URLs) stored in `calendars.results_code` by `Import::Committers::Calendar` (lookup by FIN id first, then meeting code/meeting id; a FIN `results_link` is never replaced by a non-FIN URL, a stored `results_code` is never replaced by a different one, nor are its `results_link`/`manifest_link`; a FIN id already linked to a calendar of ANOTHER meeting is a fatal `stats[:errors]` error that rolls the whole Phase 6 commit back). Commits with results also set `meetings.results_acquired`; Phase 1 preselects the meeting (and its sessions) linked to the source's FIN id (`meeting_match` in phase1.json).
- State sources: the watcher snapshot (`FedernuotoWatch::StateStore`) + DB (`DbIndex`) + files on disk (`DiskIndex`, `SourceProbe`). Files are mapped to rows by their CONTENT (`meetingURL`/`manifestURL` -> FIN id), never by predicted file names. Busy (queued/running job in the activity log) is an overlay, not a state.
- States, first match wins (`StateResolver`; next action in parentheses): `cancelled` (none), `sql_pending` (`push`), `prepare_failed` (`prepare`, "Retry"), `needs_review` (`resume_review` with `filter_state: 'review'`), `ready_to_commit` (`commit` = GET the commit summary, never a commit), `in_review` (`resume_review`), `results_ready` (`review_results`), `structure_ready` (`review_structure`), `manifest_pending` (`extract_manifest`), `committed_with_results` (none), `structure_committed` (`check_results` when the last date is past, else none), `crawled_no_manifest` (`review_header`), `archived_unlinked` (`link`), `link_not_crawled` (`crawl`), `not_linked` (none).
- Orphans (`DbIndex#orphans`): season calendars without FIN id or with a FIN id absent from the snapshot (the latter are marked and never linkable). Link candidates (`Builder.link_candidates`): orphans without FIN id and not cancelled. A `link_not_crawled` row whose dates include a candidate's date gets the `:possible_unlinked_meeting` flag (the meeting may exist from a FICR/Microplus import). `DiskIndex#board_sql_paths` lists the backfill/calendar-link SQL scripts (not sources, excluded from `unmatched`; counted in the board header).
- Jobs (all on the `background` queue: single thread/process in `config/queue.yml`, so they run strictly one at a time; enqueue only through `SeasonBoard::Scheduler`, which logs the request first and refuses a second one for a busy FIN id): `MeetingCrawlJob` (direct-URL crawl of the snapshot URL, 30-minute timeout, `SeasonBoard::CrawlOutput` checks the output), `ManifestExtractJob`, `SeasonRecheckJob` (recurring `season_board_recheck`, daily 5:15am, re-crawls past meetings still without results and retries failed automatic crawls after 20 h, max 15 per run). `FedernuotoWatchJob` (default queue) calls `SeasonBoard::CrawlPlanner` on every detected change to crawl the not-yet-crawled changed rows. Both skip `:possible_unlinked_meeting` rows. Jobs never raise and are not retried by Solid Queue; each closes its activity as done/failed; a failed enqueue is logged (board buttons: flash error). Stale queued/running entries (`ActivityLog::RUNNING_STALE_AFTER`/`QUEUED_STALE_AFTER`) are no longer busy and show a "seems stuck" badge. Manual crawls of the Sources crawler tab (`SourceCrawlJob`, priority 10) share the `background` worker and the concurrency key AND group (`SeasonBoardBackground/season_board`) with `MeetingCrawlJob`/`ManifestExtractJob`, so they queue behind the board crawls instead of being refused; `Crawler::RunWatcher` (shared by both crawl jobs) also waits up to 5 minutes for a crawl the crawler reports as running.
- Pipeline automation (phase 10, operator guide `docs/season_board.md` *Pipeline automation*): the three pipeline states come from `SeasonBoard::PipelineIndex` (3 ops queries per build: the season's `Ops::PipelineSource` rows, their `Ops::PhaseVerdict`s, the latest `prepare` `Ops::PipelineRun` of each; facts in `StateResolver::Facts#pipeline` / `Row#pipeline`, looked up by the base of the entry's active source; files without a row keep today's states, pre-09 files stay `in_review`). `SeasonBoard::PipelinePlanner` (via `PipelinePlannerJob`, queue `default`, `limits_concurrency key: 'pipeline_planner'`; enqueued by `PipelinePlannerJob.enqueue_after` at the end of `MeetingCrawlJob`, `ManifestExtractJob`, a `done` `DataFixPrepareJob` and `FedernuotoWatchJob`, by "Prepare all", and every 15 min as recurring `pipeline_planner`) queues prepares through `Scheduler.prepare!` (writes the queued `Ops::PipelineRun`, ActivityLog kind `:prepare`; refuses a leased / pending / commit-pending source) and automatic extractions through `Scheduler.extract!(origin: :auto, pdf_path:)` (an `extract` run row per attempt, max 3 failed per PDF, 20 h apart, engine preflight once per pass). It never queues a prepare for a source holding ANY edited phase (`edited_recorded?` from the verdicts, then `DataFix::Pipeline#any_edited?` on the files), a held row (`pipeline_sources.auto_prepare = false`, POST `season_board/hold`) or a source run less than 10 min ago. `DataFixPrepareJob` (queue `pipeline`, priority 10, key `data_fix_pipeline`, no retries, never raises) holds the lease `job:<job id>` for its whole run (`Pipeline#hold_lease!`), soft deadline `DataFixPrepareJob::DEADLINE` (20 min), yields to a queued commit (`prepare!(stop_if:)`), and ends `done`/`failed`/`refused`/`yielded`. `CrawlPlanner#plan_recrawl` re-crawls `structure_committed` rows under the watcher's `with_results` (20 h rate limit). Switches: `DataFix::Automation` (`automation.enabled` / `.auto_extract` / `.auto_prepare` in `Ops::Setting`, `ADMIN2_AUTOMATION=0` forces all off; without the ops DB only the master stays on), checked by the planners before every enqueue, by `SeasonRecheckJob`, and at job start for automatic work; toggled at POST `automation/switch` (dashboard system column, board header). Nothing on this side names the commit/push entry points, and the only API call reachable from a prepare is the read-only drift GET (`spec/automation_boundary_spec.rb`). Automatic paths fail closed on unreadable ops data (switch off, busy/commit pending, extraction given up, no prepare when `PipelineIndex#read_error?`); an automatic prepare takes the lease and checks edits before resolving and refuses (`source_needs_review`) a source with phase files that the resolver would rewrite; `Pipeline#invalidate!` deletes nothing while another owner holds the lease.
- Activity log: `crawler/data/season-board.json` (`SeasonBoard::ActivityLog`, kinds `crawl extract prepare`; unknown kinds in the file are ignored); the activity strip shows it on the board and on the Sources crawler tab. The Sources crawls and extractions are keyed `src:<sha1 of kind and target>` (`ActivityLog.source_key`, optional `label` shown instead of the FIN id) and a running job writes `heartbeat_at` at each poll (busy past `RUNNING_STALE_AFTER` while the heartbeat is under 5 minutes old); `Inbox::Sources::FailedJobs` ignores the `src:` entries (their end is a toast and an ops event). `SeasonBoard::Notifier` pings `AppNotificationsChannel` (needs the local Solid Cable DB; the board polls every 20 s while busy as a fallback).
- Round 2 (0.10.98-0.10.104, plan in `docs/plans/done/ops-console-improvements-plan.md`):
  - Truthful rows: `Scheduler.prepare!` passes `fin_event_id` + `run_id` to `DataFixPrepareJob`, which closes its activity entry on every exit path; `SeasonBoard::ActivityReconciler` repairs entries whose job finished or was lost (never enqueues). `PipelineIndex#fresh?` compares each verdict with the files it covers (working copy + phase files 1..N, never the LT2 once an LT4 exists); the planner skips a no-op `rebuild_stale` (`:unchanged_since_run`). A row's GET action stays enabled while a job is only queued (`ActionPaths.blocked?`; `Row#locked?` = lease or a running entry).
  - Link adoption: `SeasonBoard::CalendarIndex` (newest original 'Eventi' CSV in `calendar.new`/`calendar.done`, at most 14 days older than the watcher's `last_checked`, rows inside the season, `startURL` of the Eventi page; key = first date, last date, normalized places; one-to-one on both sides; self-check on comparable keys). Never store an adoption; never match on names. `MeetingCrawlJob` re-derives an adopted URL itself. `CrawlFailures.adopted_exhausted?` stops unattended crawls of an adopted row after 3 failures in a row.
  - FIN change chain: see CLAUDE.md (`SeasonBoard::ChangeChain`). Automatic `SourceCrawlJob`s are enqueued only by `Scheduler.calendar_crawl!`, kind `calendar` only (`AUTO_KINDS`; `calendar_results` is never automatic: `spec/automation_boundary_spec.rb`). Queue priorities on `background`: 0 operator board buttons, 10 Sources crawls, 15 automatic calendar crawl, 20 automatic meeting crawls and extractions. An automatic acknowledge writes its trace first and needs the master switch and the ops DB; the hidden-alert decision (`FedernuotoWatch::Progress.alert_shown?`) reads the switch live.
  - Clean-up: every file move goes through `Sources::Cleanup::Mover` (hard link + unlink, never overwrites, appends to the run's `MOVES.txt`); `Sources::Cleanup::Safety` holds every refusal (busy, leased, in review, edited, pending runs, young files, apply lock); `SourceProbe` facts `unparsable` / `pdf_derived` are never "result-free". New rules go in `SeasonBoard::RedundantFiles`, not in the callers.
- File safety: `DataFix::SourceResolver#supersede_manifest_copy!` keeps `.orig[-N].json` copies of the source and of each phase file it drops (every phase-file scan skips `.orig` names); `PdfManifests::Extractor` re-checks the output path right before writing and backs up any replaced output.
- Backfill: `rake season_board:backfill season=<id> [simulate=0]` links existing calendars to FIN ids and flags `results_acquired` (idempotent; applies in one transaction and registers its SQL script in the Outbox; a snapshot-predicted file name shared by different FIN ids is ignored). Apply it before relying on the automatic crawl: meetings committed before the FIN id was stored have no linked meeting on the board (`archived_unlinked`/`link_not_crawled`) and could be crawled again.

## Grid pages, toolbar bespoke content & local lookups

- Every `api_*` index (phase 15) keeps its own `APIProxy.call(...)` (exact arguments: the request specs stub them) and ends with `render_api_index(GridClass, ModelClass, result, csv_name:)` (`APIGridIndex` concern; optional `grid_params:`, `csv_columns:`, a block for extra grid class attributes). A non-200 answer renders the same page, status 200, with `Grid::APIErrorComponent` (code, detail, Retry, Settings link when unreachable) instead of the rows; nothing redirects to the dashboard; a CSV request redirects to the page. CSV header rows are always English. `render_api_error(result, rows: [])` does the same for a page without a grid (trainings).
- The views render `Grid::PageComponent(title:, model:, grid:, domain: api_grid_domain, toolbar: {...})` (header + count, edit modal, toolbar, filter form, filter labels, paginated table); slots `toolbar_extra` (buttons at the end of the toolbar, e.g. `api_meetings`, `api_team_managers`) and `actions` (page header); the block content is a bespoke body (categories clone panel; with `grid: nil`, the trainings table).
- Row drill-down links: `Grid::DrillLinkComponent(path:, icon:, label:, text: nil, kind:)` inside an `html: true` column (`drill` on meetings/teams/swimmers; meetings link the Season board row through `MeetingsGrid.board_links`, set from the domain like `ImportQueuesGrid.outbox_scripts`).
- Grid headers are never written in the grid files: `grids.<grid>.<column>` and `grids.<grid>.filters.<filter>` in `config/locales/grids.{en,it}.yml` (`<grid>` = class name without `Grid`, underscored; fallbacks: filter -> column of the same name -> `grids.defaults.*`), read at render time (`BaseGrid.default_column_options` / `default_filter_options`); `spec/grids/base_grid_headers_spec.rb` fails on a literal header or a missing key. `boolean_column` drops its options (they land in Datagrid's `query` argument), so its header can only come from the locale file.
- `Grid::ToolbarComponent` accepts a content block rendered at the end of the toolbar row — use it for page-specific buttons (see `api_team_managers/index.html.haml`).
- `GET /lookup/:domain[/:id]` (`LookupController`) serves whitelisted localhost-DB JSON lookups (seasons/teams/users, swimmers/meetings/badges since 13) for `LegacyAutoCompleteComponent` widgets and the operation forms; the remote API cannot search seasons by description. `LookupController.search_scope(model, query)` is also the entity search of the command palette.
- Command palette (Ctrl+K / Cmd+K, phase 15): `Shell::PaletteComponent` (modal at the body level of the layout, entries = `Shell::Navigation.palette_entries`, every item incl. contextual children; offline sessions get the offline items only) + `Shell::PaletteTriggerComponent` (top bar `search` slot) + `palette_controller.js`; `GET /palette/search?q=` (`Shell::PaletteController` -> `Shell::PaletteSearch`: meetings, teams, swimmers, Data-Fix sessions, max 20, local only). A new navigation item reaches the palette with no extra work.
- `TeamManagerSqlCreate` (`POST /api_team_managers/sql_create`) creates `team_affiliations`/`managed_affiliations` on localhost inside a transaction that also writes the `SqlMaker` batch file into `crawler/data/results.new/<season_id>/` — a file-write failure rolls back the local rows.
