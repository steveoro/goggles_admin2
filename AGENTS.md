# Goggles Admin2 Agent Notes

## DataFix V2 canonical source handling

- `DataFixController` maps LT2 inputs to persistent sibling `-lt4.json` working copies via `resolve_working_source_path` and `materialize_lt4_working_copy`.
- Reuse existing LT4 working copies when present; regenerate only when missing.
- Exception 2 — manifest copies give way to results: a `<base>-lt4.json` written by `PdfManifests::Extractor` (`_meta.meeting_only: true`) shares the working-copy name. When the LT2 sibling `<base>.json` later has result rows, `DataFix::SourceResolver` (whether given the LT2 or the `-lt4.json` path) backs the manifest file up as `<base>-lt4.orig[-N].json`, re-materializes the LT4 from the LT2 (Layout2To4), and deletes `<base>-lt4-phase1..5.json` plus their `data_import_*` rows. While the LT2 is still result-free (`sections: []`), the manifest copy is reused as before. File names are deliberately unchanged, because archives, `CrawlerCalendar::Row#source_state` and `DataFix::CommitArchiver` depend on them.
- When `PdfManifests::Extractor` finds the output already present: a results source is never touched (skip reason `results source already present`, even with `force`); a previous manifest output is skipped unless `force` (`output already exists`); a result-free plain working copy with no phase files is backed up (`.orig.json`) and replaced by the manifest LT4 (with phase files it is skipped unless `force`, and then backed up). Both skip reasons still archive the PDF/.txt, and `BatchRunner` lists them under `skips` in the status file.
- Manifest LT4 files carry `meetingURL` / `manifestURL` from the crawled `<base>.json` (when present and non-blank) right after `layoutType`.
- Phase review/update/add/delete actions must use the canonical source path and propagate `file_path` in redirects.
- Phase1 fixture sources use `layoutType: 4` to keep existing phase-path assumptions stable.

## Calendar meeting selection before result crawling

- `/pull/calendar_meetings?file_path=…` (checkbox icon on `.csv` files in `/pull/calendar_files`) renders one row per meeting with URL/manifest/source state; `POST /pull/process_selected_meetings` writes a `<base>-sel-<ts>.csv` subset next to the source and calls `/pull_results` on it. The ⚡ bolt icon still runs the whole-file `process_calendar_file` path.
- `CrawlerCalendar::Sheet`/`Row` (`app/strategies/crawler_calendar/`) are FAITHFUL Ruby ports of the JS crawler's `normalizeText`/`parseDaysDate`/`getOutputJSONFilename` — including quirks (`undefined-` basename for dateless rows, `2026-10-8_11-31` for `31/10-8_11`, cancelled only on literal `true`/`canc`). The predicted `manifest-<date>-<name>.pdf` must match `results-crawler.js` byte-for-byte — keep them in sync when touching either side.
- Manifest state per row: `:done` (pdf in `manifests.done/<season>/`), `:pending` (in `manifests/<season>/`, awaiting extraction), `:none`; source state reports `-lt4.json`/`.json` presence in `results.new`/`results.done`.

## PDF manifest extraction (meeting data)

- `rake manifests:extract season=<id> [engine=devin|ollama]` turns `crawler/data/manifests/<season>/manifest-*.pdf` into `layoutType: 4` sources under `crawler/data/results.new/<season>/` via `PdfManifests::Extractor`. The LLM client is resolved by `PdfManifests::ClientFactory` (param > `MANIFEST_ENGINE` env > default `devin`): `devin` spawns `devin -p` non-interactive sessions (default model `swe-2-high`, requires `devin auth login`); `ollama` uses the local Ollama server (default `gemma4:e4b`, vision fallback only when the model advertises `vision`). Successfully-extracted and already-extracted manifests (.pdf + .txt) are moved to `crawler/data/manifests.done/<season>/`; the task aborts with a warning when the engine or its configured model is not available.
- The same batch runs from the UI via `POST /pull/extract_manifests` → `PdfManifests::BatchRunner` in a Puma thread; progress is written to `crawler/data/manifests-extract-status.json` and polled through `GET /pull/extraction_status` by `manifest_extraction_controller.js`. `BatchRunner.archive` is the shared .pdf+.txt→`manifests.done` move used by the rake task; `BatchRunner.running?` combines a process flag with a 10-min status-heartbeat staleness window (the rake task does NOT write the status file, so it is not detected as busy). The selection page only accepts CSVs under `crawler/data/calendar.new/` (realpath-checked), since the crawler only moves `calendar.new` → `calendar.done`.
- Manifest LT4 files carry extra prefill keys: `venueName`, `venueAddress`, `cityName`, `poolLength`, `edition`, `maxIndividualEvents`, `manifestSessions` (one per meeting day) — `Phase1Solver` prefers them over `place`.
- Manifest files are meeting-only (no results): they can be committed as a bare meeting structure after Phase 1 (`Import::StructureValidator` gates the commit; new meetings get `manifest: true`). Results are added with a second data-fix pass on the published-results source — select the existing meeting in Step 1 and rescan sessions to avoid duplicates.
- `Lt4Builder` emits structured `issues` (retriable vs advisory) alongside `_meta.warnings`; `ProgramScanner` adds a completeness hint (program mentions vs extracted events). Retriable issues trigger ONE corrective extraction pass (`ExtractionPrompt.build_correction` feeds issues + valid event codes back to the model); the retry is kept only when strictly better. Never auto-remap unknown event codes.
- `_meta.warnings` from the LT4 source render as an info banner on the Phase 1 review page.
- Devin engine gotcha: the spawned `devin` must not see agent/IDE context env vars (`ACP_BACKEND`, `AI_AGENT`, …) — `DevinClient::SCRUBBED_ENV_KEYS` unsets them, otherwise the nested CLI reports "Not logged in" even with valid credentials. Ollama calling conventions/gotchas (must set `num_ctx`, `think:false`, `format:'json'`): `docs/pdf_processing/ollama_extraction_notes.md`.

## Season board

- Purpose: `/season_board` (`SeasonBoardController`, `app/services/season_board/**`, `app/components/season_board/`) is the weekly one-page flow for the latest MASFIN season: one row per FIN "Riepilogo Eventi" row, with the linked local meeting, a pipeline state and a single next action. Operator guide: `docs/season_board.md`.
- Link key: the numeric FIN event id (`FINEventId`, parsed from results/manifest URLs) stored in `calendars.results_code` by `Import::Committers::Calendar` (lookup by FIN id first, then meeting code/meeting id; a FIN `results_link` is never replaced by a non-FIN URL, a stored `results_code` is never replaced by a different one). Commits with results also set `meetings.results_acquired`; Phase 1 preselects the meeting (and its sessions) linked to the source's FIN id (`meeting_match` in phase1.json).
- State sources: the watcher snapshot (`FedernuotoWatch::StateStore`) + DB (`DbIndex`) + files on disk (`DiskIndex`, `SourceProbe`). Files are mapped to rows by their CONTENT (`meetingURL`/`manifestURL` -> FIN id), never by predicted file names. Busy (queued/running job in the activity log) is an overlay, not a state.
- States, first match wins (`StateResolver`; next action in parentheses): `cancelled` (none), `sql_pending` (`push`), `in_review` (`resume_review`), `results_ready` (`review_results`), `structure_ready` (`review_structure`), `manifest_pending` (`extract_manifest`), `committed_with_results` (none), `structure_committed` (`check_results` when the last date is past, else none), `crawled_no_manifest` (`review_header`), `archived_unlinked` (`link`), `link_not_crawled` (`crawl`), `not_linked` (none).
- Jobs (all on the `background` queue: single thread/process in `config/queue.yml`, so they run strictly one at a time; enqueue only through `SeasonBoard::Scheduler`, which logs the request first and refuses a second one for a busy FIN id): `MeetingCrawlJob` (direct-URL crawl of the snapshot URL, 30-minute timeout, `SeasonBoard::CrawlOutput` checks the output), `ManifestExtractJob`, `SeasonRecheckJob` (recurring `season_board_recheck`, daily 5:15am, re-crawls past meetings still without results, max 15 per run). `FedernuotoWatchJob` (default queue) calls `SeasonBoard::CrawlPlanner` on every detected change to crawl the not-yet-crawled changed rows. Jobs never raise and are not retried; each closes its activity as done/failed.
- Activity log: `crawler/data/season-board.json` (`SeasonBoard::ActivityLog`); the activity strip shows it on the board and on the Pull pages. `SeasonBoard::Notifier` pings `AppNotificationsChannel` (needs the local Solid Cable DB; the board polls every 20 s while busy as a fallback).
- Backfill: `rake season_board:backfill season=<id> [simulate=0]` links existing calendars to FIN ids and flags `results_acquired` (idempotent; applies in one transaction and stores a SQL script for the push dashboard). Apply it before relying on the automatic crawl: meetings committed before the FIN id was stored have no linked meeting on the board (`archived_unlinked`/`link_not_crawled`) and could be crawled again.

## Grid toolbar bespoke content & local lookups

- `Grid::ToolbarComponent` accepts a content block rendered at the end of the toolbar row — use it for page-specific buttons (see `api_team_managers/index.html.haml`).
- `GET /lookup/:domain[/:id]` (`LookupController`) serves whitelisted localhost-DB JSON lookups (seasons/teams/users) for `LegacyAutoCompleteComponent` widgets; the remote API cannot search seasons by description.
- `TeamManagerSqlCreate` (`POST /api_team_managers/sql_create`) creates `team_affiliations`/`managed_affiliations` on localhost inside a transaction that also writes the `SqlMaker` batch file into `crawler/data/results.new/<season_id>/` — a file-write failure rolls back the local rows.
