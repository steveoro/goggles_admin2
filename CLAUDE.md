# CLAUDE.md

See also `AGENTS.md` (checked in) for detailed notes on DataFix V2 canonical-source handling, Phase 1 pool/city rehydration, PDF manifest extraction, and the grid pages / toolbar / lookup endpoints / command palette. Don't duplicate it here. The operator's routine, end to end, is `docs/operator_guide.md`.

## What this is

Rails 8.1 / Ruby 3.4 admin UI for the Goggles framework (v7+), designed to run **only on a developer's localhost**. It mounts the `GogglesDb::Engine` (git gem `goggles_db`, which provides models and the schema) and talks to a separate `goggles_api` service through `APIProxy` (`app/strategies/api_proxy.rb`). Its main job is turning crawled/extracted meeting results into production DB rows (the "Data-Fix" pipeline), plus merge/purge/normalize maintenance tools. MariaDB via mysql2 (`config/database.yml`, socket-based, DBs `goggles_development` / `goggles_test`); schema format is `:sql` (`db/structure.sql`).

## Commands

```bash
bin/rails server -p 3000            # or: foreman start -f Procfile.dev (web + dartsass:watch)
bin/rails dartsass:watch            # CSS (dartsass), needed in dev

bundle exec guard                   # watcher the README expects green before PRs

# Crawler (separate Node service, port 7000): the crawl jobs of the Sources crawler tab and of the Season board start it
# when needed (CrawlerLauncher, also the "Start crawler" button of the Sources crawler tab)
cd crawler && npm install && npm start
cd crawler && npm test              # mocha

bin/rails solid:prepare             # create/load the local SQLite queue, cable & cache DBs (idempotent, never touches MySQL)
```

Background jobs use **Solid Queue** (workers in `config/queue.yml`: `default` for quick jobs, and single-thread `background` (Season board and Sources crawls/extractions), `maintenance` (health checks), `outbox` (push runs) and `pipeline` (Data-Fix prepare/commit jobs, PDF scans); a job on an unlisted queue never runs, `spec/config/queue_names_spec.rb` checks it); the supervisor runs inside Puma (`plugin :solid_queue` in `config/puma.rb`; set `SOLID_QUEUE_IN_PUMA=false` to opt out and run `bin/jobs` separately). ActionCable uses **Solid Cable** so job broadcasts reach the browsers. In development `Rails.cache` is **Solid Cache** (`config/cache.yml`; low-level cache only, e.g. `PdfResults::CategoriesCache` — test uses the null store). All three live on local SQLite DBs (`queue:`/`cable:`/`cache:` entries in the gitignored `config/database.yml` — see `config/database.example.yml`; files under `storage/`), each with `schema_dump: false` so a schema dump can't overwrite `db/{queue,cable,cache}_schema.rb`. Don't run a bare `bin/rails db:prepare`/`db:migrate` just for these: it would also act on the shared MySQL primary — use `solid:prepare`.

A fifth local SQLite DB, **ops** (`db/ops/<env>.sqlite3`, gitignored; `ops:` entry with `database_tasks: false` + `schema_dump: false`, so no Rails DB task ever sees it), holds the admin2-only tables (`events`, `settings`, `snapshots`, later more; models under `app/models/ops/`, hand-written migrations in `db/ops_migrate/`). It is created/migrated only by `bin/rails ops:prepare` (run last by `solid:prepare`, and by `spec/rails_helper.rb` at suite boot); see also `ops:status`, `ops:backup`, `ops:reset confirm=<env>`, `ops:rebuild`. Manual step: paste the `ops:` blocks from `config/database.example.yml` into the local `config/database.yml`; without them the app still boots and shows a setup notice. Callers go through `Ops.available?` / `Ops.safely { }` / `Ops.record_event!(kind:, ...)` (i18n `ops.events.<kind>`): an event write never fails a commit, push or job. Every request spec writes the ops test DB (its session): a second suite running in parallel can use a private ops test DB with `OPS_DATABASE_URL=sqlite3:tmp/<name>.sqlite3` (created and migrated at suite boot; only the two specs pinning the default `db/ops/test.sqlite3` path then fail). `ops:prepare` also prunes the events older than 180 days and the web sessions unused for 30 days. System specs (`spec/system`) need Chrome (no network: every asset is vendored; run `bin/rails dartsass:build` first), light theme by default, `SYSTEM_THEME=dark` for the dark one; `SKIP_SYSTEM=1` skips them.

Maintenance rake tasks live in `lib/tasks/` (`manifests`, `normalize`, `merge`, `purge`, `recompute`, `check`, `fix`, `db`, fixtures tasks). List with `bin/rails -T`; read each task's `desc` for its env-style args (e.g. `rake manifests:extract season=<id>`). Since phase 13 the operational ones (`merge`, `fix`, `purge`, `recompute`, `normalize`, `import`, `check`, `season_board`) are thin callers of the maintenance operations: `Maintenance::RakeRunner` + one adapter per task in `app/services/maintenance/rake_tasks/` (same texts, prompts, exits; runs inline, origin `rake`; `simulate=1` = script held 'not applied locally', `simulate=0` = drift gate then local apply then Outbox; needs the ops DB). Their output is pinned by recorded baselines (`spec/support/rake_parity/`, `spec/tasks/*_parity_spec.rb`); `db:run` stays terminal-only.

## Architecture

### Data-Fix pipeline (the core)
Six phases turning a results source file into production data; docs in `docs/data_fix/` (`README.md` → `PHASES.md` → `TECHNICAL.md`, `DATA_STRUCTURES.md`).
- Principle: **solve early, commit later** — entity matching happens when each phase file is built (`phase1.json`…`phase4.json` hold resolved IDs); Phase 5 stages results/laps in `data_import_*` DB tables; Phase 6 commits atomically and writes an SQL log.
- Controllers: `DataFixController` holds cross-phase utilities; per-phase controllers are in `app/controllers/data_fix/*` (sessions, teams, swimmers, events, results, commits) on a shared `base_controller` (v2 is the only flow; the `phase*_v2` flags are optional).
- Logic is split between `app/services/data_fix/**` (phase builders, cascades, issue detection, post-commit checks, source resolution) and `app/strategies/import/**` (`solvers/`, `committers/` with `committers/main.rb` as the Phase 6 entry point, `adapters/`, `team_score_extractor`, `structure_validator`, `phase5_populator`). SQL generation is `SqlMaker`.
- Source files: crawler output lands in `crawler/data/results.new/<season>/`; layoutType 4 (LT4) is the canonical format (see AGENTS.md for LT2→LT4 working-copy rules). Result-free (manifest) sources follow a shortened Phase 1 → Phase 6 chain.
- Orchestration lives in `DataFix::Pipeline` (builds, verdicts per phase, staleness by input digests, edit markers in the phase file `_meta`: an automatic build never rewrites an operator-edited phase); controllers are thin callers. The commit goes summary → `DataFixCommitJob` (`pipeline` queue, operator click only) → `Ops::CommitReport` page; `DataFix::Guards` applies the DB sync gate. Unattended prepares (phases 1-5, never a commit or push) run as `DataFixPrepareJob` on the same `pipeline` queue (priority 10 behind the commit's 0; no retries; refuses any source with an edited phase when automatic). Interactive progress goes to the non-blocking `Shell::ProgressStripComponent` (layout, `progress_strip_controller.js`) through `Import::Progress::Cable` (one `op` per request, `seq`, `done` sent by `DataFix::BaseController`'s around_action; `Import::Progress.default` is `Null`, so jobs and rake tasks never broadcast); a plain review GET broadcasts nothing.

### Other subsystems
- Sources (`/sources`; the old `/pull/...` and `/pdf/extract_txt` GET URLs redirect there for one release): season-aware tabs Results / Calendars / Manifests / PDFs / Crawler / Files (`app/controllers/sources/*`, `app/services/sources/**`, `app/components/sources/*`; season in the ops setting `sources.season_id`). Manual crawls are `SourceCrawlJob`s (`background`, priority 10, same concurrency key and group as the board crawls, `Crawler::RunWatcher`, `Sources::CrawlKinds` URL checks), PDF scans `PdfScanJob`s (`pipeline`, priority 10; outcome in `Ops::Snapshot` `pdf_scan:<sha1>`, `PdfResults::ScanState`), manifest extractions `ManifestExtractJob`s through the one path `PdfManifests::Extraction` (also `rake manifests:extract`). "Prepare" on a non-FIN source calls `SeasonBoard::Scheduler.prepare!` (it then shows in the inbox like a FIN one). Every file operation resolves its path through `Sources::FileGuard` (never outside `crawler/data`) and `Sources::FilePolicy`; the file editor validates JSON and marks a saved phase file as an operator edit. Redundant files (`/sources/cleanup`, `Sources::Cleanup::Plan` / `Apply` / `Safety` / `Mover`, also `Sources::CrawlTidy` + `Sources::CalendarTidy` after a Sources crawl and `SeasonBoard::CrawlOutput` after a board crawl; shared rule `SeasonBoard::RedundantFiles`) are only ever MOVED (to `results.backup/<season>/cleanup-<ts>/` with a `MOVES.txt`, `manifests.done`, `calendar.done`), never deleted or overwritten.
- PDFs (`docs/pdf_processing/`): `app/strategies/pdf_manifests/` turns a manifest PDF into an LT4 meeting structure (pdftotext + LLM engine — `devin` CLI default, local Ollama optional; one entry point `PdfManifests::Extraction`); `app/strategies/pdf_results/` parses a result PDF with the YAML format definitions (`PdfResults::FormatParser`, run by `PdfResults::ScanRunner` / `PdfScanJob`).
- `app/strategies/merge/` + `docs/merge/`: swimmer/team/badge/meeting merge checkers and semantics.
- Dashboard (`/`, `docs/dashboard.md`): `DashboardController` (one Turbo frame per zone, no API call), the "Needs you" inbox (`app/services/inbox/**`: `Inbox::Registry` sources registered in `config/initializers/inbox.rb`, merged by `Inbox::Builder`), the `SystemStatus::Registry` probes, the KPI strip (`KpiRefreshJob` snapshot) and the `/activity` event log; zones reloaded by `live_frames_controller.js`.
- SQL Outbox (`/outbox`, `docs/outbox.md`): every script that changed the local DB is written through `Outbox::Writer` (global sequence `Outbox::Sequence`, registry `Ops::SqlScript`, `Outbox::Reconciler` adopts files on disk) and pushed in order by `Outbox::PushJob` after an operator click; outcomes (applied / failed) need goggles_api + goggles_main 0.10.82. In tests, `Outbox.guard_test_path!` refuses writes on the real `crawler/data`: pass `data_root:`.
- Data health (`/health`, section in `docs/season_board.md`): read-only checks per season and group (`Health::Registry`, `Health::Checks::*`, `Health::SeasonRunJob` / `Health::SweepJob` on `maintenance`), findings with triage in `Ops::HealthFinding`.
- Operations (`/operations`, same section of `docs/season_board.md`): the fixes behind the findings' **Fix** buttons (`Maintenance::Registry` of `Maintenance::Operations::*`: flag cancelled, badge / swimmer / team / meeting merge, team-in-meeting, badge team / swimmer fix, meeting purge, coded names, categories clone, standard timings import, season badge fix, results dedupe, NULL swimmers fix, ranks recompute, board backfill; plus the read-only `Maintenance::Inspectors::*` of the `check:*` reports, and the season-start checklist `Maintenance::SeasonStart::Checklist` at `/operations/season_start/:season_id`). Path: prefilled form → dry run (`Operation#plan`, never writes; strategy stdout captured by `Maintenance::OutputCapture`) → operator's apply (`Maintenance::RunsController#apply` only, `Drift::Gate` scope `:operation`) → `Maintenance::RunJob` (`maintenance` queue, concurrency key `local_db_writer` shared with `DataFixCommitJob`) runs the SQL with `LocalDb::SqlRunner`, then registers it in the Outbox (`results.new/misc/`) and re-runs the health group; history in `Ops::OperationRun`. Ops setting `operations.enabled` = false hides the buttons (switch in the dashboard system column and the `/operations` header: `Maintenance.store_enabled!`, `POST operations/switch`).
- DB sync (`/db_sync`, `docs/db_sync.md`): `Drift::Fingerprint` / `Drift::Verdict` compare local and remote counts + max ids (`DriftCheckJob`, `Ops::DbFingerprint`); `Drift::Gate.check(scope:)` guards commits, pushes, board links and rake writes.
- Guided local DB restore (`/db_restore/new`, `docs/db_restore.md`): replaces the local MySQL DB with a production dump (`DbRestoreController`, `app/services/db_restore/**`, jobs `DbRestore::*Job` on `maintenance`). While it runs `DbRestore::Lock` (ops setting `db_restore.lock`) makes every request answer 503 from the ops DB only (`DbRestoreGuard`, prepended in `ApplicationController`) and every job skip (`around_perform` in `ApplicationJob`): new jobs must inherit `ApplicationJob`. Specs never start a MySQL client (`DbRestore::Commands` is faked or run with `bzip2`/`cat`).
- Season board (`/season_board`, `docs/season_board.md`): `SeasonBoardController`, `app/services/season_board/**` (state resolver, disk/DB indexes, `Scheduler`, `CrawlPlanner`), `app/strategies/season_board/` (backfill, calendar linker), jobs `MeetingCrawlJob`/`ManifestExtractJob`/`SeasonRecheckJob` on the `background` queue, activity log `crawler/data/season-board.json`; links rows to local calendars by FIN event id (`calendars.results_code`); `rake season_board:backfill`. `SeasonBoard::PipelinePlanner` (`PipelinePlannerJob`, after each crawl/extract/prepare/watcher change and every 15 min) queues the prepares and automatic extractions up to "ready to commit"/"needs review"; kill switches `DataFix::Automation` (`enabled`, `auto_extract`, `auto_prepare`, `auto_calendar`; dashboard system column, board header), `ADMIN2_AUTOMATION=0` forces all automation off. `SeasonBoard::ActivityReconciler` (top of every planner pass) closes activity entries whose job is finished or lost; `SeasonBoard::CalendarIndex` lets a row without a FIN link adopt the link of the newest 'Eventi' calendar CSV (flag `:link_adopted`, derived on every build, never stored); the board filter is remembered in the `season_board_filters` cookie (`SeasonBoard::Filters`).
- `app/services/federnuoto_watch/` + `FedernuotoWatchJob` (recurring, `config/recurring.yml`): watches the FIN "Riepilogo Eventi" page via headless Chrome (`CHROME_BIN`), stores snapshots in `crawler/data/federnuoto-watch.json`, and pushes a sticky alert to every open page through `AppNotificationsChannel` (app-wide; the broadcast HTML carries no CSRF tokens — `federnuoto_watch_controller.js` injects them). After a change `SeasonBoard::ChangeChain` runs (inside `PipelinePlannerJob` and the watcher job): `CalendarPlanner` (automatic 'Eventi' calendar crawl through `Scheduler.calendar_crawl!`, max one per 6 h + one a day) → `CrawlPlanner` (per-meeting crawls of the new or changed rows, `CrawlBudget`: at most 15 automatic crawls outstanding) → `PipelinePlanner` → `FedernuotoWatch::ParityCheck`: when `FedernuotoWatch::Parity` says every actionable row is in the pipeline, `FedernuotoWatch::Acknowledge` dismisses the alert (trace written first: events `fin.watch_acknowledged` / `fin.calendar_notice`, inbox `Inbox::Sources::FINNotice`; never automatic with the master switch off or without the ops DB).
- `crawler/`: standalone Node server (FIN, Microplus, FICR, Go&Swim crawlers) writing artifacts under `crawler/data/` and progress to `crawler/crawler-status.json`: pages and the status probe read that file, the crawl jobs (`Crawler::RunWatcher`) ask the server (`CrawlerClient#status`); the Node WebSocket broadcast has no listener left. Docs: `crawler/README.md`, `docs/crawler/`. `crawler/crawler-status.json` changes constantly at runtime — don't commit it incidentally.
- `app/strategies` and `app/grids` plus `app/etls/{sources,transforms,destinations}` are explicit eager-load roots (`config/application.rb`), so files there define top-level constants.
- API sessions: credentials are checked against the local DB (Devise), then a JWT is fetched from the API configured in the local `AppParameter` row (`framework_urls.api`). `APIProxy` never raises on connection failures (`Result#unreachable?`). The web sessions (activerecord-session_store) live in the ops DB `sessions` table (`Ops::SessionStoreSetup`; MySQL fallback while ops isn't ready), so they survive a DB restore and every request spec writes the ops test DB. If no JWT can be obtained, a localhost sign-in becomes an "API-offline" session (`session[:api_offline]`, `app/controllers/concerns/api_session.rb`) allowed only where `api_offline_allowed?` is true (Settings, Home#index) so the API URL can be fixed.
- `API` is registered as an inflection acronym (`config/initializers/inflections.rb`), e.g. `APIProxy` lives in `api_proxy.rb`.

## Front-end
Bootstrap 5.3 (vendored), native markup everywhere. The only Bootstrap 4 markup left is in the goggles_db engine GoggleCup partials (shared with goggles_main, still on BS4): `goggles_cup/_ranking` and `goggles_cup/base_timings` render them inside a `.goggles-db-partial` wrapper, served by the scoped `compat/_goggles_db_partials.scss` (spacing, text alignment, badge colours) and the `goggles-db-partial` Stimulus controller (copies `data-toggle` & co. to `data-bs-*` inside the wrapper only). `spec/bs4_leftovers_spec.rb` requires zero BS4 tokens in the app (views, components, JS, helpers, grids, SCSS) and ratchets the engine partials (`BASELINE`).
- App shell (`layouts/application.html.haml`, `app/components/shell/`): sidebar (cookie-collapsed, offcanvas below `lg`), sticky top bar (API target badge, lazy status-pill frame, theme toggle, user menu), `main.app-content[data-page=<controller_path>]`. Pages start with `Shell::PageHeaderComponent` (breadcrumbs, title, count, actions).
- `Shell::Navigation` (`app/services/shell/navigation.rb`) is the single registry for the sidebar, the breadcrumbs and the Ctrl+K command palette: a new HTML page must add an item (or a contextual child, `sidebar: false`), otherwise `spec/services/shell/navigation_spec.rb` fails.
- `api_*` grid pages: `Grid::PageComponent` + the `APIGridIndex` concern (API errors shown in place); grid headers only in `config/locales/grids.{en,it}.yml` (`spec/grids/base_grid_headers_spec.rb`).
- Status pills: `SystemStatus::Registry` probes; `:snapshot` probes only read ops snapshots written by `SystemStatus::RefreshJob`, so rendering the shell never calls the API. `Shell::StatusPillsComponent` shows one "All OK" pill when every probe is fine, else one pill per problem plus an "N OK" pill.
- Stored on/off settings use `Switch::ToggleFormComponent` (Bootstrap `.form-switch` + `toggle_submit_controller.js`; turbo-stream answers update the panels in place). Turbo hover prefetch is off app-wide (`turbo-prefetch` meta): several GETs build files or write metadata.
- Stylesheets: `base/` (tokens `--ga-*`, fonts, links without underline, helpers), `shell/`, `components/`, `pages/`, `compat/` (the engine-partial scope only); colours come from Bootstrap/`--ga-*` variables so both themes work. Built CSS `app/assets/builds/application.css` is tracked: rebuild it with `bin/rails dartsass:build` after a stylesheet change.

## Conventions
- Every Ruby file starts with `# frozen_string_literal: true`.
- Update `CHANGELOG.md` and bump the version when making user-visible changes (recent commits follow this).
- Specs: `spec/{requests,services,strategies,components,...}`; fixtures live in `spec/fixtures` and can be regenerated with the `fixtures_*` rake tasks.
- Specs that write into `crawler/data` with factory seasons leave empty `results.*/<season_id>` folders; `spec/support/crawler_data_housekeeping.rb` removes them at the end of every RSpec run (empty, numeric, not a season in the test DB, untouched for a minute).
